**Findings**

1. **P1 — The production proxy can send its token to a caller-selected server.**
   [Frontend `server.mjs`, lines 51–68](../../simple-network-monitor-frontend/server.mjs).
   Removing `/snm-api` can leave a path beginning with `//`. Passing that path
   into `new URL(path, configuredOrigin)` replaces the origin. A request shaped
   like `/snm-api//capture.example/v1/hosts` therefore leaves the configured
   backend, and the proxy adds `SNM_API_TOKEN` to that request. Two ephemeral
   loopback servers reproduced this: the unintended upstream received
   `Authorization: Bearer fake-review-token`. This also permits requests from
   the frontend server to other reachable HTTP services.

   Construct the URL by assigning pathname/search on a validated backend URL,
   restrict proxy paths/methods to the API's needs, and enforce the expected
   origin before attaching credentials. Check redirect behavior as well.
   Node explicitly recommends validating the resulting origin when a URL input
   might be absolute ([Node URL documentation](https://nodejs.org/api/url.html#new-urlinput-base)).
   Add cases for double slashes, backslashes, encoded separators, redirects,
   and ordinary host-history paths.

   URL parsing also happens outside the `try` block. The malformed path
   `/snm-api//[` produced an unhandled rejection and process exit in a local
   handler reproduction. Cover the entire asynchronous request handler with
   error handling and return a controlled 400 for malformed input.

2. **P1 — Reload validates authentication against a bind address that is not applied.**
   [Backend `main.rs:144`](../src/main.rs#L144),
   [`main.rs:166`](../src/main.rs#L166),
   [`config.rs:175`](../src/config.rs#L175).
   Start with a non-loopback bind and a token. Change the config to loopback
   without a token and reload. Validation accepts the new configuration, the
   bind change is ignored, and `apply_reloaded_config` removes authentication
   from the still-exposed listener. A focused test against the existing reload
   helper reproduces this state. Assigning `config = next_config` also loses
   the distinction between actual listener settings and configured settings
   on subsequent reloads.

   Keep immutable runtime settings separate from reloadable settings. Validate
   token changes against the actual listener and reject unsafe reloads before
   mutating shared state. Test IPv4/IPv6, token rotation, token removal, the
   explicit unauthenticated override, and repeated reloads.

3. **P1 — SSH command assembly changes the meaning of the usage script.**
   [Backend `backends/usage/mod.rs:109`](../src/backends/usage/mod.rs#L109).
   Passing `"sh", "-lc", script` as separate SSH arguments does not preserve a
   remote argument array. OpenSSH joins the remote command arguments with
   spaces ([OpenSSH manual](https://man.openbsd.org/ssh.1)). The generated first
   assignment runs inside `sh -lc`; following lines run in the surrounding
   remote shell without that assignment. In a deterministic local test with
   fake `loginctl` and `who`, running the script directly reported one console
   user; running the command assembled as SSH does reported zero. Both exited
   successfully. OS detection and UID selection can also be affected.

   Send the script through stdin to a fixed `sh -s` command, or correctly quote
   the complete remote script as one shell argument. Test executable behavior
   with fake command output for Linux, macOS, systemd sessions, empty sessions,
   and command failures. Current string-presence tests cannot catch this bug.

4. **P1 — Configuring a frontend server token removes the visitor authentication boundary.**
   [Frontend `server.mjs`, lines 67–68 and 187–193](../../simple-network-monitor-frontend/server.mjs),
   [frontend deployment instructions](../../simple-network-monitor-frontend/README.md).
   Every visitor receives the server's backend authority. The frontend permits
   `HOST=0.0.0.0` without checking for visitor authentication, even when it holds
   `SNM_API_TOKEN`. This is distinct from finding 1: an ordinary tokenless
   `/snm-api/v1/hosts` request succeeds. The joint browser/API test reproduced
   it. Loopback defaults reduce exposure, and a separately authenticated ingress
   could make this deployment intentional; none is enforced by this server.

   Define an explicit deployment/authentication model. Use authenticated ingress
   or frontend sessions for shared access, or require each visitor's backend
   token. Refuse accidental non-loopback exposure with a server token unless
   an explicit external-authentication deployment mode is configured. Document
   the requirement and test startup/authentication combinations.

5. **P1 — A transient storage error permanently loses an observed ICMP transition.**
   [Backend `modules/icmp/monitor.rs:82`](../src/modules/icmp/monitor.rs#L82).
   `check_once` advances the in-memory state before persistence. If the write
   fails, the transition is discarded. The next matching observation persists
   the new latest state without creating a transition because the in-memory
   state has already changed. A fake repository that fails exactly the first
   write reproduced an Up-to-Down latest state with no history event.

   Preserve pending transitions until persistence succeeds, or make the storage
   boundary compare and atomically update persisted state. Define retry and
   idempotency semantics so retries neither lose nor duplicate events. Retain
   the existing SQLite atomicity tests and add the monitor/repository failure
   test; the existing tests only verify atomicity inside one write.

6. **P2 — Old successful observations can be reported as current inactivity.**
   [Backend `domain/filters.rs:134`](../src/domain/filters.rs#L134),
   [`storage/sqlite/mod.rs:521`](../src/storage/sqlite/mod.rs#L521).
   Inactivity evaluation never checks the age of `snapshot.collected_at` or
   whether monitoring continued throughout the requested window. A single
   successful zero-user observation from 60 days ago was returned as satisfying
   `no_users_for=7days`. Disabling usage collection, a daemon outage, or a dead
   per-host task can leave this state indefinitely.

   Define freshness and observation-gap rules using the resolved collection
   interval. Exclude stale/disabled/insufficiently observed hosts from affirmative
   inactivity results, and expose unknown/stale state to the UI. Test stopped
   collection, long gaps, restart, disabled modules, and future timestamps.

7. **P2 — TOML error messages can disclose the API token.**
   [Backend `config.rs:28`](../src/config.rs#L28),
   [`config.rs:139`](../src/config.rs#L139),
   [`main.rs:195`](../src/main.rs#L195).
   `ApiToken` redacts `Debug`, but parse errors include original source lines.
   Parsing `api_token = ["fake-review-secret"]` reproduced a diagnostic containing
   the complete fake token. Reload logs render that error, and CLI failures
   can expose it as well.

   Render sanitized diagnostics with location and a safe explanation, excluding
   secret-bearing source snippets. Test both syntax/type failures and startup/
   reload rendering. Redaction tests should exercise the full error path,
   not only the token newtype's `Debug` implementation.

8. **P2 — `ssh_verify_host_key = true` does not explicitly enforce verification.**
   [Backend `backends/usage/mod.rs:93`](../src/backends/usage/mod.rs#L93).
   The false branch adds `StrictHostKeyChecking=no`, but the true branch leaves
   policy to the service user's SSH configuration. A matching SSH stanza can
   still disable checking. This conflicts with the application setting and
   documented guarantee. The argument inspection confirmed that the enabled
   path never sets `StrictHostKeyChecking=yes`.

   Explicitly set the strict policy for the enabled branch while preserving
   configured known-host sources. Test a permissive ambient SSH configuration.
   OpenSSH documents the strict policy and its behavior for unknown/changed
   keys ([SSH configuration manual](https://man.openbsd.org/ssh_config#StrictHostKeyChecking)).
   Also validate destinations before process execution and terminate option
   parsing: the config currently only rejects blank addresses, so an address
   beginning with `-` can be interpreted as a process option. This latter issue
   requires control of the local configuration, not an unauthenticated API call.

9. **P2 — Timeouts and admission limits do not cover the complete work path.**
   [Raw ping `mod.rs:99`](../src/backends/ping/mod.rs#L99),
   [SQLite `mod.rs:175`](../src/storage/sqlite/mod.rs#L175),
   [frontend `server.mjs`, lines 71–79](../../simple-network-monitor-frontend/server.mjs).
   Inspection shows DNS resolution occurs before the raw ping timeout; every
   database request starts a blocking task before acquiring one of four reader
   connections or the writer mutex; the proxy buffers the whole upstream body
   and supplies no application deadline or disconnect cancellation. Browser
   refresh aborts consequently do not necessarily stop backend work. SSH
   stdout/stderr are also collected without a size bound.

   Apply one probe deadline across resolution and probing, bound database
   admission before spawning blocking work, and give proxy requests deadlines,
   response limits, and disconnect cancellation. Stream responses where useful.
   Bound process output and retained error text. Test stalled DNS, a held writer,
   saturated readers, slow/oversized upstream responses, and disconnected clients.
   Tokio notes that running blocking tasks cannot be aborted and can queue after
   the thread limit ([Tokio documentation](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html)).

10. **P2 — A single-host lookup clones the entire inventory.**
    [Backend `storage/sqlite/mod.rs:254`](../src/storage/sqlite/mod.rs#L254),
    [monitor initialization](../src/modules/icmp/monitor.rs#L63).
    `host(id)` clones the full host map, then selects one entry. Each host
    performs this lookup during monitor initialization, making inventory-copy
    work quadratic across startup/reload. The clone also runs before
    `spawn_blocking`, on the async worker. `update_hosts` additionally uses a
    vector membership test inside `retain`, another avoidable quadratic path.

    Clone only the requested host under the read lock; use a set for retained
    IDs. Consider loading initial monitor state in one batch. In a local debug
    build, 100 single-host reads took 13.70 ms at 100 inventory entries,
    80.63 ms at 1,000, and 729.13 ms at 10,000. These measurements demonstrate
    scaling behavior, not production throughput limits.

11. **P2 — Frontend grouping repeatedly copies arrays and rescans the inventory.**
    [Frontend `App.tsx`, lines 742–775](../../simple-network-monitor-frontend/src/App.tsx).
    Each room insertion copies the entire existing room array. Hosts lacking
    room metadata all enter the same group, a natural worst case for reusable
    deployments. The room picker also scans all hosts once per room, even when
    its popover is closed. A local Node microbenchmark of the current grouping
    loop took approximately 3 ms for 1,000 hosts, 104 ms for 10,000, and
    1,596 ms for 20,000. Appending to buckets took approximately 0.24, 0.77,
    and 1.99 ms respectively.

    Build room buckets and counts in one pass, append to the local arrays, use
    sets for skipped-room membership, and reuse a collator/search representation
    when profiling justifies it. Add large fixtures with one room, many rooms,
    and absent room metadata. A React memo does not remove the cost when its
    inputs change on every poll.

12. **P2 — The complete refresh path scales with the entire inventory per viewer.**
    [Backend listing](../src/api/routes/mod.rs#L53),
    [SQLite listing](../src/storage/sqlite/mod.rs#L430),
    [frontend fetching](../../simple-network-monitor-frontend/src/api.ts),
    [frontend `App.tsx`, lines 615–619 and 1630–1693](../../simple-network-monitor-frontend/src/App.tsx).
    Every viewer periodically fetches all hosts. The backend clones inventory,
    loads all latest tables, filters/sorts, constructs DTOs, and serializes a
    complete array. The proxy buffers it, and React renders every matching row.
    Inactivity filters add per-host history queries. There is no listing
    pagination, conditional refresh protocol, or row virtualization.

    First remove findings 10 and 11. Then measure full refreshes with concurrent
    viewers. Add a compatible paged/server-filtered API and virtualized rows
    when required, with explicit server-wide summary semantics. Pause polling
    in hidden tabs, use completion-based refresh scheduling with backoff, and
    consider snapshots/deltas or conditional requests. Preserve export semantics
    when moving away from fetching the complete inventory. Do not infer a need
    to replace SQLite before measuring these application costs.

13. **P2 — Host details can contradict the refreshed dashboard, and failures look like valid data.**
    [Frontend `App.tsx`, lines 264–325, 573, 634–646, 962–964 and 1728](../../simple-network-monitor-frontend/src/App.tsx).
    Three focused tests reproduce separate problems: the drawer retains the
    selected `Host` object after the host list refreshes; a failed history request
    is converted into an empty history; and usage snapshots with `status=error`
    and null counts are displayed as zero users. The latter was also confirmed
    against real backend JSON in Chromium.

    Store a selected host ID and derive current details from the latest data,
    handling removal explicitly. Key history requests by host ID and connection
    and guard all completion/error paths against cancellation. Give history an
    explicit failure/retry state. Display unknown/error usage separately from
    a successful zero. Test refresh during an open drawer, host removal,
    connection switching, 401/500 history responses, and null/error counts.

14. **P2 — Accepted duration input can panic during an API query.**
    [Parser `filters.rs:367`](../src/app/filters.rs#L367),
    [domain calculation `filters.rs:144`](../src/domain/filters.rs#L144).
    `1000000years` passes duration parsing and conversion but overflows Chrono's
    date range during subtraction. A real repository query reproduced a blocking
    task panic surfaced as `StorageError::TaskJoin`. File-backed requests fail
    rather than safely returning 400; the in-memory fallback can also poison its
    writer mutex. This reproduction does not establish a whole-daemon crash.

    Use checked date arithmetic and reject unsupported query durations at the
    API boundary. Validate configuration retention/timeouts/concurrency against
    downstream representable ranges too. Add boundary/property cases, including
    zero, huge valid strings, and dates near supported limits.

15. **P2 — Retention stops for hosts that stop receiving usage writes.**
    [Backend `storage/sqlite/mod.rs:326`](../src/storage/sqlite/mod.rs#L326),
    [`schema.rs`](../src/storage/sqlite/schema.rs).
    Pruning only deletes old samples for the host currently being written.
    Removed hosts or hosts with usage disabled keep their samples indefinitely;
    latest rows for removed hosts also persist and are still scanned. ICMP and
    usage change histories intentionally have no retention, so a flapping or
    frequently changing inventory can grow without bound. This is an inspected
    growth mechanism, not a measured disk exhaustion event.

    Add bounded periodic sample cleanup independent of polling and define an
    archive/deletion policy for removed hosts. Offer configurable history
    retention if indefinite history is unnecessary, preserving the anchor
    observations needed by inactivity queries. Track database/WAL size and
    explain the maintenance/vacuum strategy. At the default five-minute usage
    interval, 10,000 enabled hosts produce 86.4 million samples over 30 days;
    that is a row-count calculation, not a disk-size estimate.

16. **P2 — Tagged release publication overwrites supposedly immutable artifacts.**

    Rerunning an old release can replace bytes under the same version tag.

    mocked `gh` responses; no real release needs to be modified for this test.

**Further improvements and test targets**

- **Monitor supervision and reload ordering:** individual host-task panics are
  logged and consumed by the ICMP/usage `JoinSet` loops. Other host tasks can
  keep the module alive, so the top-level manager never sees the partial loss.
  `/healthz` always returns OK. Add explicit per-host/module supervision and a
  separate readiness/degradation signal; test a deliberately failing host task.
  Reload also updates shared inventory before aborting old monitors and does
  not await their completion. Running blocking writes may outlive cancellation.
  Introduce generation-aware writes or drain/cancel ordering, with barrier-based
  tests for an old probe completing after a same-ID host changes address.
- **Collection truthfulness:** the shell script suppresses `loginctl` errors
  and can return successful zeros after failed observation commands. Distinguish
  an empty session list from an unavailable collector. The system ping backend
  reports full subprocess elapsed time as latency while the raw backend reports
  ICMP RTT; document or normalize this difference. Tests should execute scripts
  against fake command output and test process timeout/output/cancellation.
- **UI accessibility and resilience:** a focused test showed opening the settings
  modal leaves keyboard focus outside it. Implement focus entry, containment,
  restoration, and appropriate dialog semantics for both modal and drawer.
  Validate persisted settings instead of casting arbitrary JSON to types; wrap
  storage writes for unavailable/quota-exhausted storage. Test keyboard-only
  operation, malformed storage, and denied clipboard access. Several visible
  controls, including Notifications and the user menu, have no handlers.
- **Browser credentials and export:** `saveSettings` persists the bearer token
  in local storage indefinitely. Prefer an authenticated frontend session or
  session-scoped credentials and make any persistence explicit. OWASP warns
  against storing sensitive data in local storage because same-origin scripts
  can access it ([OWASP HTML5 guidance](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#local-storage)).
  CSV quote escaping does not neutralize spreadsheet formulas in host names or
  metadata. Add an export policy and tests for formula-leading values; the
  input currently comes from operator-managed inventory, so this is a
  downstream consumer risk rather than a demonstrated remote injection path.
- **Runtime types and architecture:** `ApiToken` has private representation but
  accepts invalid values in its constructor; `Host`, resolved module settings,
  usage counts/status, and filter durations have public mutable representations.
  Add validated constructors where invariants matter. `domain/host.rs` imports
  resolved settings from `modules`, which in turn depends on HTTP/application
  code; moving resolved value types into domain/config would better preserve
  dependency direction. `DefaultHostQueryService` is unused by the running
  application while routes directly call repositories. Either use it for actual
  orchestration or remove the unused abstraction. Avoid creating more pass-through
  layers solely for architectural symmetry.
- **Maintainability and documentation:** split the 1,755-line `App.tsx` into
  focused components, data hooks, and testable selectors; split the 1,021-line
  SQLite module by query/write/catalog responsibility. The architecture document
  mentions an `r2d2_sqlite` pool although this implementation uses a custom r2d2
  manager, and says app owns monitor loops although they live under modules.
  SQLite comments claim the catalog is immutable/lock-free although it is an
  `RwLock` updated on reload. Align these claims with the implementation and
  keep the strict verification commands in sync with `AGENTS.md`.

**One workflow for both repositories**

Treat the backend API, frontend proxy, and browser as one compatibility surface.
Keep the repositories independent if desired, but identify the exact backend/
frontend revision pair in compatibility runs. The same fixture should support
backend API tests, proxy tests, and browser tests without private inventories or
network probes.

| Layer | Add these tests | What they establish |
| --- | --- | --- |
| Rust domain/config | Checked durations, stale/gapped observations, invalid tokens/destinations, parameterized thresholds | Invariants fail safely at their boundary |
| Rust orchestration | Failed first write, task panic, cancellation during reload, same-ID address replacement | Monitoring remains complete and history remains trustworthy |
| Storage | Periodic retention for removed/disabled hosts, migration from old schemas, restart persistence, concurrent snapshots | Durable behavior matches in-memory behavior |
| Production and development proxies | Shared path/authorization contract, malformed URLs, origin escape, redirects, slow/large bodies, client abort | Both proxy implementations preserve the intended boundary |
| React with live-shaped fixtures | Drawer refresh, failed/null usage, history errors, racing requests, invalid storage, focus behavior | The UI distinguishes current, stale, empty, and failed data |
| Actual backend + built frontend + Playwright | Token-required API, real error envelopes, filters/search, host history, module-disabled states, reconnect, desktop/mobile keyboard flows | The complete deployed request/data path works |
| Load and endurance | 100/1,000/10,000 hosts; 1/10/50 viewers; ordinary and inactivity-filter queries; slow probes and writes | Measured resource limits and usable refresh latency |

Run existing fast checks on every PR, plus targeted new tests relevant to the
change. Run the joint browser fixture in each repository's CI against an
explicit counterpart revision; use a broader supported-version matrix on a
schedule. Publish pairing metadata with compatibility results. Do not silently
test only whichever counterpart happens to be newest that day.

For backend changes, preserve formatting, locked tests, Clippy with denied
warnings, warning-free rustdoc, example verification, RustSec, dependency review,
and CodeQL. Add frontend locked installation, linting of both TS and ESM, tests,
build, audit, npm Dependabot, and JavaScript/TypeScript security analysis. Keep
musl verification, absence of `DT_NEEDED`/`PT_INTERP`, byte-for-byte RPM payload
comparison, the Rocky 8 baseline, and tagged-release provenance gates.

Measure p50/p95/p99 listing latency, bytes transferred, frontend render/filter
time, event-loop delay, process RSS/thread count, reader/writer wait time,
per-host observation age, probe scheduling delay, and database/WAL growth.
Use deterministic slow fakes for load tests instead of contacting real hosts.
The existing four-reader WAL design and bounded probe concurrency are useful
foundations; first address unnecessary copying, request fan-out, and admission.

An indicative capacity constraint is `hosts × average probe duration / interval`
concurrent probe slots, before database/process overhead. With 10,000 SSH hosts,
five-second timeouts, and the default 32 slots, one all-timeout sweep needs at
least about 26 minutes, versus the default five-minute interval. This is a
worst-case scheduling calculation, not measured production performance. Make
overdue probes visible rather than interpreting successful API polling as
healthy collection.
